Case study · Delivery flow

Where the work waits.

A product team kept missing its dates, and nobody could say where the time went. I built a small pipeline that turns a Jira export into flow metrics, finds the stage where work queues up, and forecasts delivery dates from the team's own history instead of from guesses.

Simulated data. Built on simulated data, modelled on problems from my work in program delivery. The team, its 343 work items and every number on this page are fictional. No data from SuperAGI or any other employer was used.

Data
343 simulated Jira items, 26 weeks, a 9-person team
Tools
Python, SQL in DuckDB, Apache ECharts
Code

01The problem

A team that is busy all the time, and still late.

Picture a 9-person product team: a product manager, six developers and two testers, working on three product streams called Payments, Onboarding and Reporting. They track their work on a Kanban board, a board with one column for each stage of work where every card is one task. Each card moves from Backlog to Ready, In Progress, Code Review, QA and finally Done.

For the first 14 weeks the team had no rule about how much to take on at once. Developers started something new whenever their own work was waiting for review, so work in progress (WIP), the number of items started but not yet finished, kept growing. In week 15 the team set WIP limits, a maximum number of cards allowed in a column at one time: 5 in In Progress, 4 in Code Review and 3 in QA.

Two measures come up on every chart below. Cycle time is how many days one item takes from the moment someone starts it to the moment it is done. Throughput is how many items the team finishes in a week. The questions are the ones every delivery team is asked: where does work wait, did the WIP limits help, and when will the next 30 items be done?

This is close to my own work. As Technical Program Manager at SuperAGI I kept the backlog in Jira, introduced 2-week sprints and coordinated developer pull requests from review to merge (see that role). This project is not from that job. It uses simulated data to show how I would measure the same kind of flow.

02The board, replayed

Every day of the 26 weeks, one slider away.

Drag the slider to see the board at the end of any day, or press play. Each card is one work item. Cards that have been started are coloured by their age, which is how long ago someone started them, compared with how long finished items took. The board opens on the day with the most work in progress.

03Cumulative flow

A queue you can see getting thicker.

A cumulative flow diagram stacks the number of items in each stage, day by day. The bottom band grows as work is finished, and the thickness of each band above it is the number of items sitting in that stage. A band that keeps getting thicker is a queue that keeps growing. The chart starts at Ready, the point where the team commits to an item, and the line on it follows the board slider. Click the chart to move the board to that day.

04Cycle time

From "it depends" to a promise you can keep.

Each dot is one finished item: when it was finished (across) and how many days it took (up). The lines are percentiles. A percentile says what share of items finished within a number of days: the 85th percentile line is the time that 85 out of every 100 items beat. Grey dots were started before the WIP limits and green dots after, and each group has its own lines.

05Throughput and WIP

Less started at once, the same amount finished.

The first chart shows how many items the team finished each week. The second shows WIP, the items in In Progress, Code Review and QA at the end of each day. They are separate charts on purpose: they measure different things, and putting them on one chart with two scales would suggest a link that the scales invent.

06Where the time goes

Code Review is where work waits.

Each bar splits the average cycle time into the stages an item passed through. Blocked time, when an item was flagged as stuck, is pulled out on its own wherever it happened, so the parts of each bar add up exactly to the average cycle time.

Flow efficiency is the share of cycle time in which someone was actually working on an item. Jira cannot see that, so I count In Progress and QA as working time and Code Review and blocked time as waiting. On that generous reading flow efficiency was about 69% before the limits and 69% after: the limits shortened every stage rather than changing the mix. The real figure is lower, because time in In Progress also includes waiting while a developer juggles several items.

Blocks were rare but expensive. 26 of the 246 finished items were blocked at least once, blocked time was 5.3% of all cycle time, and one item lost 26.5 days to blocks.

07When will it be done?

A forecast from data, not from a guess.

How long would the next batch of items take? Instead of asking the team for an estimate, this runs 10,000 Monte Carlo simulations. A Monte Carlo simulation answers a question by playing it out many times with random draws: each run picks a week at random from the team's last 12 weeks of throughput, adds up the finished items week after week, and records when it reaches the total. The calculation runs in your browser.

A single date hides how much the team's pace changes from week to week, so it is wrong more often than it looks. A range shows how likely each date is, so you can choose how much risk to accept, and I would commit to the 85% date.

The forecast assumes that the coming weeks look like weeks 15 to 26, when the team finished between 6 and 13 items a week, and that new items are about the same size as past ones. It should be re-run every week as new data arrives.

08Findings

What this data says, and what I would do next.

Three findings
  1. Code Review is where work waits. In this data set, items started before the limits spent 2.9 days in Code Review on average, against 1.8 in QA and 0.6 blocked. The review queue grew from about 2.4 items in week 5 to 9.0 in week 14, as more work was started than reviewed.
  2. Limiting WIP cut cycle time without slowing the team. In this data set, throughput stayed at about 9.2 to 9.7 items a week while the median cycle time fell from 9.9 to 6.7 days. That is what Little's Law predicts when average WIP drops by about a third.
  3. The slowest items were mostly blocked ones. In this data set, 7 of the 12 items that took longer than 18.9 days had been blocked at least once, while only 26 of all 246 finished items were ever blocked.
What I would recommend as program manager
  1. Keep the limits and add one working rule. Before anyone starts a new item, they check the Code Review column first. The size of the review queue becomes a standing point at the daily stand-up.
  2. Watch item age every day. Any item older than 8 days, the 85th percentile, is raised at stand-up, and every blocked item gets an owner who chases the blocker the same day.
  3. Plan with forecasts, not single estimates. I would re-run the forecast every week with the newest throughput and share both the 50% and the 85% date with stakeholders, so a deadline comes with an honest level of risk.
09How it is built

Five steps, all of them open.

The analysis is written in SQL and runs in DuckDB, a small database that runs SQL directly on files on a laptop, with no server. Python only generates the data, runs the SQL files in order and writes one JSON file, a plain-text data format, for this page. The same pipeline runs on a real Jira export: the README lists the columns it needs.

  1. simulate.pySimulates the team day by day with a fixed random seed and writes a Jira-style export: issues, status changes and blocked flags. View ↗
  2. import_jira.pyTurns any Jira export, simulated or real, into three clean tables and maps workflow status names onto six stages. View ↗
  3. sql/01 to 11Eleven SQL files with plain-English comments: throughput, cycle time percentiles, the daily board, time in each stage, flow efficiency, blocked time, item age and the Little's Law check. View ↗
  4. run_analysis.pyRuns the SQL files in order and writes the results to one JSON file. View ↗
  5. This pageDraws the charts with Apache ECharts. Only the board replay and the forecast are calculated in your browser. Read the README ↗
